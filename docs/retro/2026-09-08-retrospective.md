# 振り返り 2026-09-08 — POC 3 面と生成パイプライン構築

対象: ゲーム基盤 → 手描きドット絵 → 却下 → Gemini 生成パイプライン → 768×672 化 → デザイン資料化、までの 1 日。

## うまくいったこと

| 事項 | なぜ効いたか |
|------|-------------|
| 物理・レベル・テキスト折り返しを先にユニットテスト化 | 後の大改修（解像度 3 倍、UI スクリーン描画）で回帰を即検出できた |
| ボット自走（`window.__game` を DevTools から操作）を E2E 代わりにした | 3 面のクリア到達と実行時エラーの有無を 1 分で確認できる |
| 生成の「仕様表 → 生成 → 後処理 → manifest → テスト」を全部スクリプト化 | 素材 117 点を再現可能に作れた。失敗しても raw と prompt が残る |
| 生成物の実測（セル数・色数）に基づいて解像度を決めた | 主観で決めた 3 回の解像度はすべて外れた。実測値だけが正解を出した |
| デザイン資料（キャラシート・ステージ俯瞰）に仕様値を載せた | 「いい感じ」を言わなくても合否を議論できる土台になった |

## 失敗と学び（重要度順）

### 1. 品質判定を主観で語った
- 事象: 「敵はいい感じです」と報告し、ユーザーに「賛同しない。基準も参照画像もない」と指摘された
- 原因: 基準文書を作る前に作業を進め、自分の判定を根拠なく述べた
- 学び: **基準（数値・参照画像）を先に文書化し、報告は基準への適合・テスト・スクリーンショットで行う。主観語は使わない**

### 2. 手描き（ピクセル文字列）で SNES 水準に届くと思った
- 事象: 16×24 → 24×32 → 32×48 と 3 回描き直しても「ファミコン水準」と評価された
- 原因: 線の引き方・陰影の置き方の技量が不足。自動シェーディングで補おうとしてプラスチック質感になった
- 学び: **キャラの造形品質が要求される場合、LLM の手描きドット絵は採用しない。画像生成＋後処理に最初から振る**

### 3. スプライト寸法の根拠を持たずに決めた
- 事象: 16×24 を「聖剣 2 相当」と説明し、「どこ基準か」と問われて答えられなかった
- 原因: 記憶からの雑な数値。実機は聖剣 2 ≈ 24×32、クロノ 16×35、超魔界村 28×32
- 学び: **寸法・色数などの数値は出典（実機のスプライト実寸表、参照画像の計測）を添えてから使う**

### 4. 参照画像の取り違え
- 事象: 指示された参照フォルダの画像（クォータービューのオフィス）を側面視ゲームの基準として計測し始めた
- 学び: **参照を計測する前に「何の基準として使うか」を 1 行で確認する**

### 5. 生成モデルへの契約（1 セル = N px、テンプレート）が守られると思った
- 事象: 「1 セル 16px」「チェッカー柄テンプレート」を指示しても、モデルは自前の 4〜6px 格子で描いた。テンプレートは絵を劣化させた
- 学び: **モデルの密度は制御できない前提で、後処理で実測する。サイズは「2 フレーム横並び」で安定させる**

### 6. 後処理でセル幅を誤推定し、1 セルおきに間引いた（実質 1/2 縮小）
- 事象: 周期推定が 2 倍のピッチを返し、それを「セル抽出」と思い込んで進めた。ユーザーの「縮小は絶対ダメ」の後に判明
- 原因: 推定値を目で検証しなかった（ズーム画像を見れば 1 分で分かった）
- 学び: **推定パラメータは必ず拡大画像で目視確認する。周期推定は約数・倍数に誤爆するので、境界投影＋規則格子のスナップで局所追従する**

### 7. 解像度決定を 2 回やり直した（256×224 → 512×448 → 768×672）
- 原因: 6 の誤計測に基づいて 512×448 を提案・承認まで取ってしまった
- 学び: **承認を取る前に、根拠となる計測を再確認する。誤りが分かったら即座に撤回して再提案する（今回はそうした）**

### 8. 「首なしユニコーン」など欠損表現をモデルが拒む
- 事象: 3 回生成しても頭が描かれた
- 学び: **モデルが描き足す表現（欠損・破損）は 1 回で見切り、別表現に置き換える。再生成は 2 回まで**

### 9. 帽子・衣装のフレーム間一貫性
- 事象: 帽子が 2 フレーム目で脱落、衣装変更を無視
- 学び: **付属物・衣装は後処理（色抽出して合成、色相規則で置換）で作る前提にする。差分抽出は体のスケールが変わるため不可**

### 10. 並列実行で生成台帳が競合
- 学び: **台帳の書き込みはロックするか、生成は 1 プロセスで逐次実行する**

### 11. 背景の密度が層ごとにバラついた（空 3・遠 2・中 1）
- 原因: 1 リクエストの横幅が約 250 セルしかない
- 学び: **背景は「両端に余白のある層を複数枚」生成して連結する。密度差は仕様に明記し、暫定と分かる形で残す**

### 12. カタログが「並べただけ」だった
- 事象: 「体系的でない」と指摘
- 学び: **資料はキャラシート／敵シート／タイル／背景レイヤー／ステージ俯瞰／UI の章立てで、絵に数値（寸法・色数・tick・当たり判定・スクロール係数）を重ねる**

## 次に同じ仕事をするときの手順（要約）

1. 基準文書（寸法・色数・出典）と参照画像の計測 → 承認
2. 生成パイプライン（仕様表・生成・後処理・manifest・テスト）を空で通す
3. 主人公ベース 1 枚で密度を実測 → 解像度決定 → 承認
4. 素材を種別ごとに生成し、都度カタログで検査
5. 報告は「テスト結果＋スクリーンショット＋台帳番号」
